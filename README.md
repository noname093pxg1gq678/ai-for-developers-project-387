## Стек

- **Контракт:** TypeSpec → OpenAPI 3.0 → клиентский SDK (`@hey-api/openapi-ts`); генерация одной командой, дрейф проверяется в CI
- **Бекенд:** Node.js + TypeScript + Fastify; данные в памяти процесса
- **Фронтенд:** React (Vite) + TypeScript + Mantine; API-клиент генерируется из OpenAPI
- **Тесты:** Vitest (юнит и API через inject) + Playwright (e2e-браузерный сценарий против настоящего сервера)
- **Инструменты:** mise (версии и задачи), hk (git-хуки), oxlint + oxfmt (линт и форматирование)
- **Сборка и запуск:** Docker; деплой на Railway

## Установка

Требуется [mise](https://mise.jdx.dev/). Команды проекта описаны в [AGENTS.md](AGENTS.md).

```bash
git clone https://github.com/noname093pxg1gq678/ai-for-developers-project-387.git
cd ai-for-developers-project-387
mise run setup   # инструменты, npm-зависимости, git-хуки
mise run dev     # бекенд http://localhost:3000, фронтенд http://localhost:5173
```

Все проверки: `mise run check` - линт, типы, сборка, юнит-тесты, e2e против настоящего сервера, свежесть генератов. Эту же команду запускает CI на каждый push.

## Использование

Локально: приложение - http://localhost:5173, бекенд (только API) - http://localhost:3000. Панель владельца доступна только по прямому URL http://localhost:3000/admin - переходов между поверхностями нет (см. [ADR 0001](docs/adr/0001-disconnected-surfaces.md)).

В контейнере - один образ: бекенд раздаёт собранный фронтенд и API на одном порту :3000 (порт берётся из переменной окружения `PORT`):

```bash
docker build -t call-booking .
docker run --rm -p 3000:3000 call-booking
```

Работающая версия: https://call-booking-production-85a10cee.up.railway.app

## Агент в GitHub

В issues работает агент: комментарий с командой запускает агента в GitHub Actions (`.github/workflows/agent.yml`), ответ публикуется комментарием в том же issue.

- **Событие:** `issue_comment` с типом `created`
- **Модель:** OpenCode Go, `opencode-go/glm-5.3-flash`; ключ модели - в секрете репозитория `OPENCODE_API_KEY` (ключ OpenCode Go из console.opencode.ai)
- **Скиллы:** агент работает с теми же скиллами, что и локальный - `.agents/` и `docs/agents/` приезжают из чекаута репозитория
- **Команды:** комментарий, начинающийся с `@agent`, `/oc` или `/opencode`; текст после префикса передаётся агенту как запрос
- **Результат:** ответ агента - комментарий в issue, лог прогона - в Actions

Доступ и share: команду выполняет только доверенный комментатор - collaborator с правами write, maintain или admin (проверка через collaborators API в guard-джобе). Боты (включая самого агента, отвечающего от github-actions[bot], - воркфлоу не зацикливается) и комментаторы без прав не доверенные. Секреты боты и форк-комментаторы не получают: ключ модели доступен только agent-джобе доверенного прогона, guard-джоба работает без секретов, ответы публичны в issue.

Кроме команд в комментариях, PR получают авторевью: `.github/workflows/pr-review.yml` запускает агента-ревьюера на события PR.

- **Событие:** `pull_request` с типами `opened`, `synchronize`, `reopened`; новое событие PR отменяет устаревшее ревью (`concurrency: pr-review-<номер PR>`, cancel-in-progress)
- **Фильтр (guard-джоба, без секретов):** ревью только для веток своего репозитория (`head.repo.full_name == github.repository`) - PR из недоверенного форка секрет модели не получает. Авторов-ботов НЕ фильтруем: PR самого агента (автор github-actions[bot]) тоже получает авторевью
- **Модель:** та же OpenCode Go через обычный CLI (`opencode run`), не github-интеграция
- **Что делает агент:** читает `REVIEW.md` (критерии ревью календаря), тело PR со ссылками на спеку/issue, diff PR и статусы CI; замечания - по критериям `REVIEW.md`, каждое содержит файл, строку, условия ошибки и последствие; форматирование кода не ревьюится (это линтер); при отсутствии подтверждённых дефектов ревью прямо об этом сообщает
- **Результат:** текст ревью готовит модель, публикует отдельный модель-фри шаг через `gh pr comment`; авторевью код не меняет - правки только по команде человека
- **Права и таймаут:** `contents/issues/actions/checks/statuses: read` + `pull-requests: write`; таймаут джобы 15 минут

Каналы обратной связи командного агента (`.github/workflows/agent.yml`):

- **Общий комментарий** в issue или PR - событие `issue_comment (created)`: PR = issue, команды работают в обоих местах
- **Построчный комментарий** к строке кода в PR - событие `pull_request_review_comment (created)`: агент получает из позиции файла файл, строку и окружающий diff
- **Бюджет команд:** guard-джоба считает командные комментарии доверенных не-ботов в PR (оба канала, комментарии ботов не считаются); лимит 3 на PR - сверх лимита агент не запускается, публикуется причина `limit_exhausted` с последним SHA и ссылкой на логи
- **Причины отказа:** `limit_exhausted`, `timeout`, `infra`, `agent_failed` - публикует отдельный модель-фри шаг
- **Правки в PR:** агент на PR-команде работает в head-ветке PR; Publish work пушит её и обновляет PR (пуш под PUSH_TOKEN владельца: PR от github-actions[bot] не запускает новые воркфлоу и требует ручного подтверждения, PR от владельца запускает их сразу); правки не отменяются (`agent-issue-<номер>`, cancel-in-progress: false)
- Таксономия событий: авторевью и интерактивный агент - раздельные события; авторевью не меняет код и не реагирует на построчные комментарии (это интерактивный канал), правки агент делает только по команде человека

Команды в комментариях: общий комментарий = `issue_comment`, построчный = `pull_request_review_comment` с контекстом из позиции.

Кроме команд в комментариях, новые обращения разбираются автоматически: автотриаж реализует `.github/workflows/triage.yml`.

- **Событие:** `issues` с типом `opened` - только что созданные обращения
- **Фильтры (guard-джоба, без секретов):** issues от ботов пропускаются (служебные обращения платформы размечены заранее), а также issues, у которых уже есть хоть одна метка - готовые тикеты (`ready-for-agent`) и разобранные не трогаются; автотриаж запускается только для обращения без единой метки
- **Права triage-джобы:** `contents: read`, `issues: write`; checkout с `persist-credentials: false`. Прав на пуш нет: код не меняется
- **Что делает агент:** по скиллу triage анализирует обращение и проставляет через `gh issue edit` метки `needs-triage` и категорию (`enhancement`, `bug` или `question`), затем публикует triage-заметку комментарием с дисклеймером _(generated by AI)_ и вопросами к репортёру, если они нужны

## Плановый аудит приложения

Регулярная проверка опубликованного приложения (Railway) по расписанию: `.github/workflows/audit.yml` собирает Lighthouse-отчёт, агент разбирает его и создаёт issue по конкретной находке.

- **Расписание:** событие `schedule` с cron `17 3 * * *` - раз в сутки, 06:17 по Москве; рядом `timezone`-эквивалент не нужен (UTC-выражение пересчитано в московское время). Дублирующее событие `workflow_dispatch` позволяет проверить сценарий вручную без ожидания ночного запуска. Файл лежит в основной ветке; GitHub может задерживать или пропускать запуски по расписанию, поэтому ручной прогон - основной способ проверки
- **Сбор (`collect`):** chromium из playwright + `lighthouse@12` против деплоя, категории performance/accessibility/best-practices/seo. Отчёт JSON сохраняется артефактом прогона и в коммиты не попадает. Падение сбора не роняет джобу: недоступность приложения - это данные об отсутствии, агент обязан разметить их отдельно (это не подтверждает исправление дефекта)
- **Разбор (`analyze`):** агент читает отчёт из артефакта, оцени категории (порог 0.9) и упавшие аудиты; по каждой находке ищет дубли среди открытых issues (дубль не создаётся, находится существующее), среди закрытых issues проверяет повторное появление исправленной проблемы (оформляется как регрессия со ссылками на прежнюю задачу и исправляющий PR); отсутствие данных размечается отдельно. Итог каждого прогона публикуется комментарием в тикете аудита с ссылкой на прогон
- **Права:** `contents: read`, `issues: write`, `actions: read`; пуш-прав нет - аудит не меняет код. `timeout-minutes` на обе джобы, `concurrency: audit-app` (cancel-in-progress: false) - параллельные аудиты не наслаиваются
- **Результаты запусков:** первый ручной прогон ([run 44931711977](https://github.com/noname093pxg1gq678/ai-for-developers-project-387/actions/runs/44931711977)) нашёл 3 находки (контраст текста карточек, отсутствие meta description, отсутствие robots.txt) и создал issue #26, #27, #28 - дубли и регрессии не найдены. Учебный прогон ([run 44931969344](https://github.com/noname093pxg1gq678/ai-for-developers-project-387/actions/runs/44931969344)) с явно обозначенной учебной находкой создал учебный issue #29. Повторный учебный прогон ([run 44932174005](https://github.com/noname093pxg1gq678/ai-for-developers-project-387/actions/runs/44932174005)) с той же находкой дубля не создал - существующий #29 признан покрывающим
- **Вывод о работе агента:** агент без пользователя корректно извлёк находки из Lighthouse-отчёта, уточнил места в коде (PublicPage.tsx), честно проверил дубли и не стал создавать повторные задачи; учебный режим и дедупликация работают как задумано. Слабое место: агент опирается на поиск по ключевым словам - находку, сформулированную иначе, он может посчитать новой; это приемлемо, человек на триаже видит полный отчёт в комментариях тикета

## Агент в GitLab (self-hosted)

Тот же агент-контур существует в виде пакета переноса на self-hosted GitLab (тикет #15): GitHub-воркфлоу продолжает работать, GitLab-версия активируется при переносе проекта. Пакет собран «положи и подключи»: живая привязка выполняется отдельно, когда владелец предоставит адрес инстанса и токены.

### Что живёт где

- **Вебхук-релей** (`gitlab/relay/`) - отдельный сервис, живёт вне приложения и вне репозитория проекта: собственный Docker-образ, слушает `POST /webhook` от self-hosted GitLab (события `issue` и `note`), проверяет секрет вебхука, применяет guard-фильтры и для доверенных запускает пайплайн через GitLab API
- **Пайплайн** (`.gitlab-ci.yml`) - три джобы в репозитории проекта: `guard-dotenv` (сводит переменные релея в dotenv-артефакт, секретов нет), `agent` (OpenCode CLI + скиллы из чекаута + `glab`), `publish` (пуш ветки токеном доставки + MR через API)
- **Трекер** - `glab` вместо `gh` (инструкция: `docs/agents/issue-tracker-gitlab.md`); агентские правила для GitLab-контура - `gitlab/agent-rules-glab.txt` (GitHub-версии не тронуты)
- **События:** `note` в issue с командой `@agent` / `/oc` / `/opencode` - запуск агента; новый `issue` без меток - автотриаж. Ответ агента публикуется комментарием в том же issue

### Guard-фильтры

Доверенное событие: автор не бот, участник проекта с ролью Developer+ (проверка через GitLab API релейным токеном), для `note` - команда с непустым текстом после префикса (кириллические гомоглифы префикса допускаются), для `issue` - отсутствие меток. Ответ релея: 202 - принято, 403 - не доверенный, 204 - не команда (без деталей наружу). Guard-логика идентична GitHub-версии (`.github/scripts/agent-guard.sh`) и покрыта тестами (`mise run test:relay`).

### Ограничения и безопасность

- `timeout` на каждой джобе (agent 20m, guard и publish 5m), `resource_group: issue-$IID` - прогоны одного тикета не пересекаются (аналог GitHub concurrency)
- CI_JOB_TOKEN вбит раннером в remote чекаута: модель могла бы его извлечь, поэтому agent-джоба делает `git remote remove origin` до запуска модели. Коммиты модели упакуются в bundle-артефакт, пуш и MR делает `publish`-джоба
- Токен пуша модель не видит: PUSH_TOKEN существует только в publish-джобе. Токен агент-джобы (AGENT_GITLAB_TOKEN) имеет scope `api` без `write_repository` - метки, комментарии и ответы да, пуш нет

### Порядок подключения

1. Перенести репозиторий на self-hosted GitLab: `.gitlab-ci.yml` активируется автоматически (пайплайны на push отключены правилом `workflow: rules` - собирается только по событию от релея)
2. Поднять релей: `docker build -t gitlab-relay gitlab/relay` и запустить с переменными из чек-листа ниже; вебхук GitLab -> `https://<релей>/webhook` на события `issue` и `note` с секретом `WEBHOOK_SECRET`
3. Создать три project access token'а и CI/CD-переменные (все masked + protected, кроме адреса)

### Чек-лист переменных и токенов владельца

| Что                    | Где                                  | Зачем                                                                                        |
| ---------------------- | ------------------------------------ | -------------------------------------------------------------------------------------------- |
| Адрес GitLab           | GitLab -> релей, CI                  | `GITLAB_URL` релея, вебхук и remote                                                          |
| `WEBHOOK_SECRET`       | CI/CD-переменная + настройка вебхука | Проверка запросов вебхука релеем                                                             |
| `GITLAB_TOKEN` (релей) | env релея                            | Project access token, scope `api`: участники и запуск пайплайна                              |
| `OPENCODE_API_KEY`     | CI/CD-переменная agent-джобы         | Ключ модели (OpenCode Go из console.opencode.ai)                                             |
| `AGENT_GITLAB_TOKEN`   | CI/CD-переменная agent-джобы         | Project access token, scope `api` (без `write_repository`): метки, комментарии, ответ агента |
| `PUSH_TOKEN`           | CI/CD-переменная publish-джобы       | Project access token, scope `api` + `write_repository`: пуш ветки и MR; модель его не видит  |

Раннер: docker executor с доступом в сеть (mise.run, npm registry, API GitLab). Минимальная версия GitLab для правил на dotenv-артефактах (`$TRUSTED`, `$WORK_PUBLISHED`) - 16.x.
