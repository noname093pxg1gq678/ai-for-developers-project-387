Проведи плановый аудит приложения по Lighthouse-отчёту audit-report.json.

Правила разбора:
1. Прочитай audit-report.json (он в рабочей копии): категории (performance, accessibility, best-practices, seo), оценки, упавшие аудиты (score < 0.9).
2. Если TRAINING_FINDING = true - вместо реального разбора используй учебную находку: «Performance score 45: LCP 8.2s на странице записи» (явно учебные данные, не подтверждённый дефект приложения).
3. По каждой находке проверь дубли среди открытых issues: glab issue list --search "<ключевые слова находки>". Если открытое issue по той же проблеме есть и новых сведений нет - не создавай дубль, только упомяни его в выводе.
4. Новой находки нет среди открытых - создай отдельный issue через glab issue create: проблема (что и где), предлагаемое действие, связь с отчётом (ссылка на прогон и путь к отчёту в артефактах). Для учебной находки пометь issue словом «учебный» в заголовке и укажи, что это не подтверждённый дефект.
5. Повторное появление исправленной проблемы: среди ЗАКРЫТЫХ issues (glab issue list --closed) проверь, нет ли по той же проблеме закрытого issue, исправленного MR-ом. Совпадение находки с прежней задачей и исправляющим MR оформи как регрессию: в новом issue ссылки на оба и пометка «регрессия».
6. Отсутствие данных: если отчёт пустой, повреждён или приложение недоступно - обозначь это отдельно и явно. Недоступность НЕ подтверждает исправление дефекта; issue по находке в этом случае не создавай.
7. Итоговый вывод: находка либо отсутствие находок либо отсутствие данных, что сделано (issue создан / дубль не нужен / нет находок / нет данных), ссылка на прогон (CI_PIPELINE_URL). Код не меняй, ветки не создавай.

Работа ведётся в GitLab: используй glab (GITLAB_TOKEN и GITLAB_HOST уже заданы), не gh.
